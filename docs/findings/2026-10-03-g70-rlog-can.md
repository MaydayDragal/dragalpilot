## Findings

1. **LKAS11 checksum is the CRC8 variant: confirmed (observation).** 100% of the stock camera's LKAS11 frames (`0x340`, ~19k frames, every segment, buses 0 and 2) match `hyundai_checksum(dat[:6] + dat[7:8])`. Neither sum variant matches any frame. This supports the port's `CHECKSUM_CRC8`.
2. **SCC origin (camera vs radar): NOT determinable from these logs.** Buses 0 and 2 carry the same traffic at the same rates, all messages including SCC11–14 (`0x420`/`0x421`/`0x50a`/`0x389`), FCA11/12 and HDA11/LFAHDA_MFC (`0x484`/`0x485`). The harness relay was not isolating the camera, as expected when the device is not in a car safety mode. The `CAMERA_SCC` hypothesis is still unverified for this car. External, unverified for this car: the upstream PR's author ran this platform with the same camera and radar FW.
   - If `CAMERA_SCC` were wrong, carstate would read cruise messages from bus 2 that are absent once the relay isolates the camera. The expected symptom is CAN errors and no engagement rather than silent misbehaviour. **This is a hypothesis: not tested.**
3. **Derived CarParams** (`get_params` + `get_params_sp` on the logged fingerprint and FW; identical on all routes): flags `CAMERA_SCC, CHECKSUM_CRC8, SEND_LFA, USE_FCA, HAS_LDA_BUTTON`; safety `hyundai`, safetyParam 8 (`CAMERA_SCC`), safetyParamSP 4 (HAS_LDA_BUTTON); `enableBsm=True`; `pcmCruise=True`, no openpilot long; `dashcamOnly=False`.
   - The fingerprint seen at boot is also passthrough (same relay state), so these are the flags the device would derive (inference from the code path and this data).
   - `radarUnavailable=False` comes from sunnypilot `_get_params_sp`, which sets it for every camera-SCC platform (`opendbc/car/hyundai/interface.py` L183–184). The platform has no `MANDO_RADAR`, so there is no radar DBC and `RadarInterfaceExt` is used. That is shared sunnypilot behaviour, not port-specific.
4. **CarState parsing:** `canValid` was never false and `canTimeout` never set after a 2 s warm-up (~24k frames over 3 routes). This only covers static signals (parked).
5. **Panda safety rx (hyundai, param 8):** 0 invalid rx messages out of ~1.53M, and safety-tick rx checks stayed valid. The car's checksums, counters and timing are accepted by the pinned safety code. No openpilot steering or long tx exists in these logs, so **tx and limit behaviour is untested**. The 484 blocked tx are the device's own UDS fingerprint queries replayed under the hyundai mode, none with controls allowed.
6. **Bus 1** carries CAN-FD-sized frames (32 and 16 bytes) at `0x51`, `0x201`–`0x21f`, `0x240` and `0x251`, not Mando radar tracks (`0x500`+). Nothing in the port consumes bus 1. Its purpose is unknown.
6a. **Classic CAN vs CAN-FD (observation, `E:\DragalPilot\logs\canfd-state-20261003.log`).**
   - Buses 0 and 2: frames are at most 8 bytes, and panda `canState0/2.canfdEnabled` is never true (500 kbps).
   - None of the Hyundai CAN-FD platform messages appear on buses 0–2 (`0x50`, `0x110`, `0x12a`, `0x1a0`, `0xea`, `0x1cf`, `0x1aa`, `0xa0`, `0x1fa`, `0x40`, `0x35`, `0x100`, `0x2a4`). The one exception is `0x130`, which is an 8-byte frame here. What `0x130` is on this car was not checked.
   - Bus 1: the panda switches `canfdEnabled` to true after the first FD frames (BRS on, 500k/2M).
   - So the control-relevant buses are classic CAN, which fits the port's non-CAN-FD `HyundaiPlatformConfig`. A separate CAN-FD network is visible on bus 1; its role is unknown.
7. Route `3ea363e27d`: MDPS reported `steerFaultTemporary` for the whole ~10 s (car likely just powered on). This is an observation only.
