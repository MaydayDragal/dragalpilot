## 4. Device procedure (each step needs the preconditions at the time)

Preconditions: the user confirms the device's **current IP address** and that it is **inactive** (offroad, not driving; ideally ignition off or the device out of the car). One SSH connection at a time. The address and key are as in the latest handoff (key `~/.ssh/id_ed25519_dragalpilot`).

**Stage 0: install (device inactive)**
1. Read-only pre-state snapshot, saved to `E:\DragalPilot\deploy\g70-20261004\pre-state.log`:
   - `git -C /data/openpilot rev-parse HEAD`, branch and status
   - params `DisableUpdates`, `UpdaterTargetBranch`, `UpdaterState`, `AlphaLongitudinalEnabled`, the NNLC toggle, `IsOffroad`
   - `/data/safe_staging` contents
   - offroad CPU snapshot (`top -bn1 | head -20`, one shot)
   - Abort if HEAD ≠ `0b2c431d`, or if the tree is dirty, or if the device is onroad.
2. Copy the bundle to `/data/tmp/` over SSH, then check its sha256 on the device.
3. `cd /data/openpilot && git bundle verify <bundle> && git fetch <bundle> dragal/custom:dragal/custom && git checkout dragal/custom`. Verify HEAD = `7e9d0755d9` and the tree is clean.
4. **Param write (needs approval in this plan):** `DisableUpdates=1`.
   - Why: the updater fetches `UpdaterTargetBranch` from `origin`. Our local branch isn't there, so it would fail and retry every 5 minutes (needless background work). Leaving updates on would also eventually move the device off the recorded baseline.
   - The launcher already refuses to install a staged update over a modified `.git`, so the install is protected either way (`launch_chffrplus.sh` L46–49).
5. **Reboot (separate explicit authorization at that moment)** so all processes load the new code.
6. After the reboot (still inactive): HEAD/branch check, `DisableUpdates` check, and one offroad `top` snapshot compared with step 1.

**Toggles for the whole validation (user decisions):** alpha longitudinal **off** (user, 2026-10-04); NNLC **off** (its model would fall back to the older G70's model). All other toggles stay as recorded in the pre-state snapshot.

**Stage 1: parked, ignition on, no engagement.** The user is in the car; it is in Park.
- Expected: the UI shows the car recognized and no "dashcam mode"; no alerts other than normal ones.
- Afterwards, with the device offroad, pull that route's rlogs (rlogs only) under the existing approval pattern, then check offline:
  - carParams `GENESIS_G70_2024`, `fuzzyFingerprint=False`, `dashcamOnly=False`
  - pandaStates safety model `hyundai`, param 8
  - **SCC11/SCC12 present on bus 2 and absent on bus 0 with the relay engaged.** This is the first direct evidence for `CAMERA_SCC`.
  - CarState `canValid` throughout
  - device load vs baseline
- **Stop criteria:** CAN errors, a wrong fingerprint, SCC on bus 0 only (that would mean `CAMERA_SCC` is wrong), or excess load. In that case, roll back.

**Stage 2: supervised drive, NOT engaged.** The user drives normally with stock SCC as desired. Check offline: CarState speed, gear, buttons and cruise state agree with what the user saw, there are no steering faults, and `canValid` holds throughout.

**Stage 3: first engagements (only after Stages 1–2 pass and the user agrees).** Daylight, dry, low traffic, a straight or gently curved road, hands on the wheel, short engagements. Afterwards, analyse requested vs measured torque (LKAS11 vs MDPS12), `steerFaultTemporary`, oscillation, and lane-centering quality.
- **Abort immediately (driver takes over and disengages)** on any unexpected steering input, oscillation, warning, or fault.
- The steering tune (steerRatio, torque) is unvalidated. Any retune is a separate, bounded change with its own review.
